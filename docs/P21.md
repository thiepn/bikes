# P21 — Compatibility Engine & Build Lab Foundation

## Objective

Turn Bike Atlas's semantic component architecture into an explainable compatibility system and establish the first trustworthy Build Lab.

P21 deliberately does **not** begin with arbitrary real-world components or a visual drag-and-drop configurator.

The first requirement is more fundamental:

> Bike Atlas must be able to explain why a component fits or does not fit.

## Compatibility model

P21 adds:

```text
engine/compatibility/types.ts
content/compatibility/reference.json
domain/compatibility/catalog.ts
domain/compatibility/evaluate.ts
domain/compatibility/build-state.ts
components/build/BuildLabPanel.tsx
scripts/validate-compatibility.mjs
```

The engine works from:

```text
host bike
  ↓
build slot
  ↓
explicit interface requirements
  ↓
candidate part interface values
  ↓
compatible / incompatible / unknown
  ↓
human-readable reasons
```

## Three-state result

Compatibility is not represented as a simple boolean.

```text
compatible
incompatible
unknown
```

### Compatible

Every interface modeled for the slot is present and matches.

### Incompatible

At least one modeled interface is known and does not match.

### Unknown

No modeled interface conflicts, but one or more required interface values are missing.

This third state is essential for future imported components.

Bike Atlas must never convert missing specifications into an assumed fit.

## Requirement types

P21 supports two primitive compatibility rules.

### Exact match

Examples:

```text
front axle
12x100-thru = 12x100-thru

bar control family
drop-integrated = drop-integrated
```

### Numeric range

Example:

```text
Road R1 tire envelope
25–35 mm

candidate
30 mm → match
45 mm → mismatch
```

This foundation can later be expanded with richer compound constraints without changing the Build Lab's result model.

## Safe P21 build scope

P21 only exposes component groups for which the current archetype data can support understandable reference interfaces:

```text
Front wheel
Rear wheel
Front tire
Rear tire
Handlebar
Seatpost
Saddle
Left pedal
Right pedal
```

That is **9 build slots per bike**.

P21 intentionally does not yet expose Build Lab swaps for:

- cranksets;
- bottom brackets;
- cassettes;
- chains;
- derailleurs;
- shifters;
- brake calipers;
- rotor sizing/adapters;
- suspension forks;
- rear shocks;
- headsets.

Those systems require more detailed interface data before Bike Atlas can make a responsible compatibility claim.

## Current modeled interfaces

### Front wheel

Checks:

```text
wheel format
front axle
disc interface
```

### Rear wheel

Checks:

```text
wheel format
rear axle
freehub / transmission family
disc interface
```

### Tire

Checks:

```text
bead-seat diameter
reference tire-width envelope
```

The width range is explicitly a **Bike Atlas reference envelope** representing the currently modeled rim/frame/fork combination.

It is not manufacturer tire-clearance data.

### Handlebar

Checks:

```text
stem clamp diameter
control family
```

P21 distinguishes:

```text
drop-integrated
flat-clamp
```

so a 31.8 mm clamp match alone cannot incorrectly make a drop bar compatible with a flat-bar control system.

### Seatpost

Checks:

```text
post diameter
```

### Saddle

Checks:

```text
rail interface
```

### Pedals

Checks the side-specific pedal thread.

Left and right remain distinct slots rather than pretending thread direction is interchangeable.

## Reference interface data

All P21 compatibility values are tagged conceptually as:

```text
bike-atlas-reference
```

They describe the fictional Bike Atlas archetypes.

They are not claims about a named commercial bicycle.

Examples of current reference architecture include:

```text
Road R1
front axle     12x100 thru
rear axle      12x142 thru
bar family     drop-integrated
seatpost       27.2 mm

Gravel G1
front axle     12x100 thru
rear axle      12x142 thru
bar family     drop-integrated
seatpost       27.2 mm

MTB M1
front axle     15x110 thru
rear axle      12x148 thru
bar family     flat-clamp
seatpost       31.6 mm

Urban U1
front axle     9x100 QR
rear interface internal-gear-hub
bar family     flat-clamp
seatpost       27.2 mm
```

These choices exist to create a coherent reference learning model, not to establish universal bicycle standards.

## Cross-bike behavior

The engine now produces meaningful cross-bike compatibility decisions.

### Road R1 + Gravel G1 front wheels

The modeled interfaces match:

```text
622 wheel format       ✓
12x100 thru axle       ✓
center-lock disc       ✓
```

Result:

```text
compatible
```

### Road R1 + MTB M1 front wheel

```text
622 wheel format       ✓
host 12x100
part 15x110            ✕
center-lock vs 6-bolt  ✕
```

Result:

```text
incompatible
```

### Gravel G1 + Urban U1 47 mm tire

The current Gravel reference envelope is:

```text
35–50 mm
```

The modeled 47 mm Urban tire therefore passes the dimensions currently represented.

Result:

```text
compatible
```

This **does not certify** unmodeled real-world rim-width, casing, mudguard, tread, pressure or frame-clearance details.

### Road R1 + Gravel G1 45 mm tire

Road reference envelope:

```text
25–35 mm
```

Candidate:

```text
45 mm
```

Result:

```text
incompatible
```

### Urban U1 + MTB M1 handlebar

Both current reference bars use:

```text
31.8 mm clamp
flat-clamp control family
```

Result:

```text
compatible
```

### Urban U1 + Road R1 drop bar

The clamp diameter matches but the control family does not:

```text
31.8 mm            ✓
flat vs drop       ✕
```

Result:

```text
incompatible
```

This demonstrates why compatibility needs multiple interfaces rather than one dimension.

## Build Lab

A new **Build** action is available in Explore.

The Build Lab has two levels.

### Slot navigator

The left side selects the host slot.

Selecting a slot also highlights the corresponding host component on the existing 3D bicycle.

### Candidate library

Each slot shows the four current Bike Atlas reference components for that semantic role.

Candidates are grouped by result:

- compatible;
- unknown;
- incompatible.

Selecting a candidate opens a full explanation.

Example:

```text
Gravel G1 front wheel
on Road R1

Wheel format
host   622
part   622
match

Front axle
host   12x100-thru
part   12x100-thru
match

Disc interface
host   center-lock
part   center-lock
match
```

## Draft build

Only candidates with:

```text
status = compatible
```

can be applied to the draft.

Unknown candidates are **not** treated as safe.

Incompatible candidates remain visible because understanding why something does not fit is one of the main educational goals of the Build Lab.

The draft tracks only deviations from the reference bicycle.

Users can:

- replace a slot;
- restore one slot;
- reset the entire draft;
- jump back to modified slots.

## Shareable drafts

Opening Build Lab creates:

```text
build=1
```

Modified slots are serialized into:

```text
buildParts=
```

For example conceptually:

```text
/?bike=road-r1
&build=1
&buildParts=front-wheel=part.gravel.front-wheel;seatpost=part.urban.seatpost
```

`URLSearchParams` handles the actual escaping in the browser.

When a draft is loaded:

1. the bike profile must exist;
2. the slot must exist;
3. the part must exist;
4. the compatibility engine re-evaluates it;
5. only `compatible` selections are accepted.

A manually edited URL therefore cannot force an incompatible component into the logical build.

## P21 3D boundary

P21 does **not** transplant donor geometry between the procedural bike models.

The Build Lab stores:

```text
logical build state
```

rather than:

```text
fully reassembled donor meshes
```

The existing 3D bike is still useful because choosing a slot highlights the physical location being evaluated.

Actual mesh substitution and assembled visual builds belong to a later phase after component assets and attachment transforms are robust enough.

## Meaning of “compatible”

A P21 compatible result means:

> Every interface currently modeled for this Bike Atlas slot matches.

It does **not** mean:

> Bike Atlas has certified the real component for installation.

Unmodeled constraints can include:

- hidden frame/fork clearance;
- rim internal width;
- actual tire casing/tread;
- cable or hose routing;
- fastener length;
- torque;
- structural load;
- adapter requirements;
- accessory interference;
- manufacturer restrictions;
- warranty requirements;
- legal requirements.

The UI states this boundary directly.

## Current graph size

Independent audit of committed reference data:

```text
host bikes                    4
build slots per bike          9
reference donor parts        36

host × candidate evaluations 144

compatible                   90
incompatible                 54
unknown                       0

broken host refs              0
broken donor refs             0
```

The `unknown` count is zero because every P21 reference candidate is intentionally complete for the limited interfaces used in its slot.

The engine retains the unknown state for future incomplete/imported parts.

## Validation

P21 adds:

```text
scripts/validate-compatibility.mjs
```

It validates:

- one compatibility profile per current bike;
- nine slots per host;
- host component existence;
- source bike existence;
- source component existence;
- unique part IDs;
- requirement shape;
- valid numeric ranges;
- installed reference self-compatibility;
- complete authored candidate interface data;
- known cross-bike pass/fail regressions;
- explainable three-state evaluator;
- shareable draft serialization;
- Build Lab model-boundary text;
- Build Lab viewer routing;
- Escape behavior.

It is included in:

```bash
npm run validate:domain
```
