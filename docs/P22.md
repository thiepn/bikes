# P22 — Build Lab 3D Assembly, Component Transforms & Expanded System Compatibility

## Objective

Turn P21's logical compatibility draft into a visible assembled bicycle while expanding the compatibility model only where the existing Bike Atlas component architecture can support explicit rules.

P22 adds two major capabilities:

1. **3D donor assembly**
2. **expanded stem + rotor compatibility**

The Build Lab is now backed by one authoritative build state shared by:

```text
URL
Build Lab
compatibility engine
3D scene
```

## 3D assembly architecture

P22 does not transplant arbitrary meshes from one prototype tree into another.

Instead it adds a normalized assembly layer:

```text
compatible draft selection
        ↓
host attachment registry
        ↓
hide host-owned semantic meshes
        ↓
render donor proxy geometry
        ↓
mount at host-local transform
```

This gives Bike Atlas deterministic host geometry without pretending the current procedural prototypes are production interchange assets.

## Visual attachment registry

P22 adds:

```text
content/compatibility/visual-attachments.json
engine/compatibility/visual-types.ts
domain/compatibility/visual.ts
```

Each host bike defines:

- its prototype yaw;
- one attachment record per Build Lab slot;
- host-local position or from/to transform;
- wheel/tire radius where needed;
- semantic component IDs owned by the slot.

Current size:

```text
4 host visual profiles
12 attachments per host
48 attachment records
```

## Slot-owned host meshes

A build slot may own more than its top-level semantic component.

For example, replacing a front wheel hides:

```text
front-wheel
front-rim
front-hub
```

while preserving:

```text
front tire
front rotor
front axle
```

unless those slots are independently modified.

This lets combinations compose correctly.

Example:

```text
Gravel wheel
+ Urban-compatible tire
+ Road rotor
```

can be represented as three separate build selections rather than one monolithic wheel assembly.

## Full hiding vs Workshop removal

P22 introduces a separate semantic state:

```text
hiddenIds
```

Build replacement uses:

```text
visible = false
```

for the replaced host semantic groups.

This is intentionally separate from Workshop `removedIds`, which uses a very faint ghost representation to teach disassembly.

Therefore:

```text
Workshop removal ≠ Build replacement
```

and P22 does not change Workshop behavior.

## Donor visual profiles

Every source bike now has a normalized donor visual profile.

The profile carries source-bike visual traits such as:

- spoke count;
- rim thickness;
- hub dimensions;
- tire thickness;
- handlebar style;
- handlebar width;
- seatpost thickness;
- saddle dimensions;
- pedal dimensions;
- stem thickness;
- accent identity.

Current donor profiles:

```text
Road R1
MTB M1
Urban U1
Gravel G1
```

## Donor proxy renderer

P22 adds:

```text
components/build/BuildDonorOverlay.tsx
```

The renderer supports:

```text
wheel
tire
handlebar
tube
saddle
pedal
rotor
```

### Wheels

A donor wheel renders:

- source-style spoke count;
- source rim thickness;
- source hub dimensions;
- host wheel radius and axle location.

### Tires

The host wheel radius remains authoritative while tire thickness comes from the donor family.

This makes a road tire, gravel tire and MTB tire visibly different even when mounted to a host wheel with the same bead-seat family.

### Handlebars

P22 renders four normalized source shapes:

```text
road drop
gravel flare
flat
swept
```

They mount to the host cockpit anchor.

### Seatposts and stems

These use authored host-local `from → to` attachment vectors.

Donor thickness remains visible while host placement stays correct.

### Saddles and pedals

Host position is preserved while source-bike dimensions/appearance are rendered.

### Rotors

Rotor diameter comes from the donor compatibility data.

The visual proxy scales the rotor accordingly, making a 140/160/180/203 mm reference rotor visibly different.

## Authoritative build state

P21's Build Lab originally owned its own draft.

P22 moves draft ownership into:

```text
BikeViewer
```

The flow is now:

```text
URL buildParts
     ↓ decode
sanitize against active host
     ↓
effectiveBuildSelections
     ├─ BuildLabPanel
     ├─ BikeScene
     └─ URL serialization
```

This prevents the UI, URL and rendered bicycle from drifting apart.

## Build sanitization

P22 retains P21's safety rule:

- bike must exist;
- slot must exist;
- part must exist;
- result must be `compatible`.

It also adds canonicalization:

> Selecting the host's already-installed reference component is treated as no modification.

Therefore an edited URL such as:

```text
buildParts=front-wheel=part.road.front-wheel
```

on Road R1 collapses back to an unchanged build rather than hiding and redrawing the reference wheel.

## Host-scoped drafts

Build selections are cleared when a workflow intentionally changes the primary host bike.

This prevents a Road draft from silently becoming a Gravel, MTB or Urban draft merely because some cross-bike selections happen to remain compatible.

The active host is always authoritative.

## Stem compatibility

P22 models:

```text
steerer clamp
handlebar clamp
```

The current Bike Atlas reference stems use:

```text
28.6 mm steerer clamp
31.8 mm handlebar clamp
```

so the four current reference stems are compatible at the interfaces modeled in P22.

Stem length and rise remain fit/geometry variables rather than compatibility gates.

## Rotor regression examples

### Road R1 + Gravel G1 front rotor

```text
center-lock      ✓
160 mm           ✓

→ compatible
```

### Road R1 + Urban U1 front rotor

```text
center-lock      ✓
180 mm           ✕

Road host envelope = 140–160 mm

→ incompatible
```

### MTB M1 + Road R1 front rotor

```text
MTB host     six-bolt
Road rotor   center-lock

→ incompatible
```

P22 still does **not** claim full braking-system compatibility.

Unmodeled brake details include:

- caliper geometry;
- frame/fork brake mount;
- adapter stack;
- pad track;
- hose/control compatibility;
- manufacturer rotor limits.

## Visual accuracy boundary

P22 is a real assembly-system proof, but the donor geometry is still normalized procedural proxy geometry.

It proves:

- slot replacement;
- host attachment transforms;
- semantic hiding;
- composable independent component swaps;
- source-family visual differentiation;
- URL → state → render consistency.

It does **not** yet prove:

- exact production GLB component transforms;
- manufacturer CAD interchange;
- cable/hose rerouting;
- suspension kinematics after swaps;
- chainline changes;
- wheel/tire collision simulation;
- true mechanical clearance.

Those remain future Build Lab work.

## Validation

P22 expands:

```text

```

to cover all 12 slots and stem/rotor regressions.

It also adds:

```text
scripts/validate-build-visuals.mjs
```

which checks:

- one visual host per bike;
- one donor visual profile per bike;
- attachment count equals compatibility slot count;
- unique attachment slots;
- hidden semantic component existence;
- valid wheel/tire position + radius;
- valid tube from/to anchors;
- valid position anchors;
- donor visual dimensions;
- donor profile availability for every reference part;
- all proxy visual kinds;
- full semantic hiding;
- BikeScene donor mounting;
- single authoritative viewer build state;
- controlled Build Lab state;
- Build Lab proxy-geometry disclosure.

Both validators are part of:

```bash
npm run validate:domain
```
