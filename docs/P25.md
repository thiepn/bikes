# P25 — Build Optimization, Goal-Based Configuration & Constraint Solver

## Objective

P25 combines Bike Atlas compatibility, system-health, geometry, gearing, and Physics models into one inspectable build optimizer.

A returned configuration must:

1. pass slot compatibility;
2. resolve modeled P23 system dependencies;
3. respect the selected geometry guard;
4. stay within the component-change budget;
5. improve the selected goal score relative to the current bicycle.

Mechanically blocked builds are never returned as final recommendations.

## Optimization goals

P25 defines five explicit goal models:

- Speed
- Climbing
- Mixed Surface
- Comfort
- Utility

Each goal lives in content/optimizer/goals.json with visible feature weights whose absolute magnitudes sum to 1.0.

### Speed

Prioritizes flat-road reference speed, low CdA, low mass, useful top gearing, and a lower / less-upright reference contact point.

### Climbing

Prioritizes 8% grade reference speed, low mass, genuinely low gearing, gear range, and useful hardpack performance.

### Mixed Surface

Balances hardpack performance, tire volume, low gearing, stable geometry, braking leverage, gear range, and mass.

### Comfort

Prioritizes less-aggressive contact points, tire volume, moderate bar width, stable geometry, and mixed-surface usability.

Comfort deliberately does not reward incidental mass savings.

### Utility

Prioritizes upright contact points, tire volume, stable geometry, internal-gear utility where the host supports it, practical surface performance, broad gearing, braking leverage, and reasonable mass.

## Hard constraints

Goal score cannot override:

- incompatible slot interfaces;
- a blocking P23 system issue;
- maximum allowed component changes;
- the selected geometry guard;
- locked current Build Lab changes.

Warnings are allowed but penalized.

## Bounded companion-aware search

P25 uses a bounded beam search over the curated Bike Atlas donor graph rather than enumerating the full theoretical Cartesian product.

Searchable consequential slots are:

- front wheel
- rear wheel
- front tire
- rear tire
- handlebar
- stem
- front rotor
- rear rotor
- seatpost
- fork
- front caliper
- rear caliper
- crankset
- rear transmission
- rear derailleur

Saddles and pedals remain manually swappable in Build Lab but are intentionally excluded from optimization because the current reference model would mostly treat them as minor mass changes.

## Temporary blocked states

A small blocked-state lane is retained during search so companion changes can resolve a partial conflict.

Example on Road R1:

1. Gravel rear transmission passes the Road transmission slot.
2. Its 44T largest sprocket exceeds the Road derailleur 36T maximum and its total-capacity requirement exceeds the Road derailleur reference capacity.
3. That intermediate state is blocked but retained.
4. Adding the compatible Gravel derailleur raises the reference maximum to 46T and total capacity to 50T.
5. The complete state becomes coherent and can be ranked.

This prevents greedy part-by-part pruning from destroying valid multi-part solutions.

## Search bounds

Current search settings:

- change budget: 1–5
- beam width: 36
- coherent lane: up to 28 states per depth
- temporary blocked lane: up to 8 states per depth

Blocked intermediate states receive an additional search penalty but are never accepted as final recommendations.

## Geometry guards

### Strict

Maximum change relative to the active starting build:

- head angle: 0.6 degrees
- trail: 8 mm
- grip horizontal position: 20 mm
- grip vertical position: 20 mm
- wheelbase: 15 mm

### Balanced

Maximum change:

- head angle: 1.5 degrees
- trail: 20 mm
- grip horizontal position: 45 mm
- grip vertical position: 45 mm
- wheelbase: 35 mm

### Open

No optimizer-level geometry delta rejection. Compatibility and system-health constraints still apply.

The comparison is against the active starting build, not blindly against the stock host.

## Preserve current changes

The Preserve my current modified slots control locks any Build Lab slot already modified before optimization.

This allows the solver to optimize around manually chosen components.

## Reference Physics scenarios

Each candidate is measured using the active build-adjusted Physics profile.

Flat reference:
- rider power: 250 W
- rider mass: 75 kg
- smooth asphalt
- grade: 0%

Climb reference:
- rider power: 250 W
- rider mass: 75 kg
- smooth asphalt
- grade: 8%

Hardpack reference:
- rider power: 220 W
- rider mass: 75 kg
- hardpack gravel
- grade: 0%

These scenarios exist for consistent educational comparison, not rider-specific prediction.

## Optimization metrics

Candidates can be scored from:

- bike mass
- CdA
- flat speed
- climbing speed
- hardpack speed
- lowest gear ratio
- highest gear ratio
- total gear range
- average tire width
- brake-leverage reference
- bar width
- saddle-to-grip drop
- trail
- wheelbase
- internal/external transmission architecture

## Scoring

Feature values are normalized to bounded 0–1 references.

Signed weights are supported. Speed uses a negative upright weight, so the model rewards a less-upright reference position instead of incorrectly treating more upright as faster.

Penalties:

- 1.25 score points per component change
- 1.5 score points for an attention/warning final state
- 12 search-score points for a temporarily blocked intermediate state

## Improvement-only recommendations

A final build must beat the active starting build after penalties.

Current rule:

candidate score > baseline score + 0.05

If nothing improves the bicycle under the selected constraints, P25 reports:

No improved coherent result under these constraints.

It does not populate the list with worse builds.

This matters especially for MTB M1, whose authored donor graph is intentionally narrow.

## Explainability

Each returned build exposes:

- total goal score
- improvement over current score
- number of changed slots
- P23 health
- top score contributions
- exact changed components
- metric deltas against the current build
- explicit gains and costs

The recommendation is therefore inspectable rather than a black-box label.

## Apply flow

Apply optimized build writes the recommendation into the canonical buildSelections state.

Apply + inspect in Build Lab writes the same selections, closes Optimize, and opens Build Lab.

The same resulting build continues into:

- the 3D scene
- Geometry Lab
- Physics Lab
- buildParts URL state

No optimizer-owned duplicate bike state exists.

## URL state

P25 adds:

- optimize=1
- optGoal
- optChanges
- optGuard
- optPreserve=1

The actual custom bicycle remains in buildParts.

Deep links restore the selected goal's own default change budget and geometry guard when explicit overrides are absent.

## Current donor-space character

Road and Gravel have broad overlap across wheels, drivetrain, braking, cockpit, and seatposts.

Urban has meaningful tire, cockpit, rotor, caliper, and seatpost alternatives while keeping its internal-gear host architecture.

MTB intentionally remains narrower: most major drivetrain, wheel, brake, tire, and fork interfaces are MTB-specific, while cockpit alternatives remain available.

The optimizer reports that limitation rather than treating incompatible donor parts as options.

## Validation

P25 adds scripts/validate-optimizer.mjs and registers it in npm run validate:domain.

The validator locks:

- five goal definitions
- goal order and uniqueness
- allowed feature IDs
- normalized absolute weight totals
- goal-specific defaults
- Speed lower-position preference
- Comfort posture-focused weighting
- meaningful compatible search alternatives per host
- the Road wide-range companion-change regression
- bounded coherent/blocked beam architecture
- compatibility engine integration
- P23 system-health integration
- P23 build-aware Physics integration
- P24 geometry integration
- P24 gearing integration
- hard geometry guards
- preserve-current behavior
- improvement-only ranking
- baseline score exposure
- transparent UI copy
- canonical build-state application
- URL routing and Escape behavior
- Geometry / Optimizer mutual exclusion

## Model boundary

P25 optimizes only fictional Bike Atlas reference data.

It is not:

- manufacturer purchasing advice
- price/value optimization
- structural certification
- warranty compatibility
- live component availability
- personal bike fitting
- medical or ergonomic advice
- race strategy
- measured wind-tunnel optimization

It is a transparent educational configuration solver over the Bike Atlas model.
