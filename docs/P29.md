# P29 — Account-Synced Portfolios, Cross-Device Recovery & THIEPN Ecosystem Integration

## Objective

P29 promotes the P27 saved Build Portfolio from browser-only persistence to an optional THIEPN Account-backed cross-device document while preserving Bike Atlas as a guest-first, local-first application.

The active bicycle, temporary Build Lab draft and current learning session remain local application state. Only explicit saved Portfolio entries sync.

## Production identity boundary

Canonical product:

- Bike Atlas
- `thiepn/bikes`
- `https://thiepn.dev/bikes/`
- OAuth callback: `https://thiepn.dev/bikes/auth/callback/`
- Core namespace: `bikes`

Bike Atlas is usable without an Account.

When the Account OAuth client is configured, signed-in users can sync saved Portfolios through THIEPN Core.

## OAuth

The browser is a public OAuth 2.1 client.

P29 uses:

- Authorization Code + PKCE;
- S256 code challenge;
- mandatory state validation;
- app-local access/refresh-token storage;
- refresh-token rotation;
- verified Account identity via `/auth/v1/user`;
- local app sign-out.

Bike Atlas never performs a direct Google login.

The production client ID is injected through:

`NEXT_PUBLIC_BIKES_ACCOUNT_CLIENT_ID`

If the client ID is absent or invalid, Account controls remain inactive and Bike Atlas continues in local-only mode.

## Portfolio document

Each saved build now includes:

- immutable entry id;
- host bike id;
- display name;
- sanitized component selections;
- source;
- savedAt;
- updatedAt.

Existing P27 entries migrate deterministically with:

`updatedAt = savedAt`

The P27 localStorage key is intentionally retained so upgrading does not strand existing saved builds.

## Core document sync

The complete Portfolio is one atomic document.

Server constraints:

- schema version 1;
- maximum 32 saved builds total;
- maximum 8 per bicycle;
- maximum 24 component-selection keys per build;
- maximum 128 KiB mutation payload.

Every write carries:

- mutationId;
- baseRevision;
- complete document.

The Core database owns revision increment and returns either:

- applied + new revision; or
- conflict + authoritative remote document.

## Conflict and recovery

P29 does not use last-write-wins.

If a dirty local Portfolio is based on a stale revision:

1. the local candidate is copied into bounded recovery storage;
2. the authoritative cloud Portfolio is restored;
3. the UI reports the conflict;
4. the user may explicitly restore the recovery copy;
5. that restored copy is marked dirty against the latest cloud revision and can then be intentionally synced.

At most five recovery copies are retained locally.

This prevents stale devices from silently resurrecting builds deleted elsewhere.

## Offline and failure behavior

Local storage remains the primary immediate interaction path.

If Account verification or Core sync is unavailable:

- Portfolio creation, rename, delete and comparison continue locally;
- P28 Markdown/JSON export remains available;
- cloud state is not guessed or overwritten;
- the UI reports that local data is unchanged.

## Ecosystem registration

P29 registers Bike Atlas in:

- THIEPN Core app registry;
- THIEPN Product Registry v2;
- THIEPN Account app registry;
- Account manifest and app-data permissions.

Account permissions are limited to:

- basic identity;
- read own Bike Atlas cloud Portfolio;
- update own Bike Atlas cloud Portfolio.

## Deployment

Bike Atlas is statically exported from Next.js and deployed by GitHub Pages as:

`https://thiepn.dev/bikes/`

The production build uses a `/bikes` base path under GitHub Actions.

The OAuth client ID comes from the repository variable:

`BIKES_ACCOUNT_OAUTH_CLIENT_ID`

Until that public OAuth client is registered, production remains intentionally local-first rather than shipping a fake authentication path.

## Validation

P29 adds `scripts/validate-sync.mjs` to the full domain gate.

It protects:

- PKCE session construction;
- exact callback URL;
- refresh/token behavior;
- Core Portfolio routes;
- revision/CAS mutation boundary;
- recovery-copy behavior;
- P27 local migration;
- Portfolio UI integration;
- static Pages routing;
- deployment variable wiring.

## Remaining activation boundary

The only Account-specific value that cannot be derived from source is the Supabase Auth public OAuth client UUID.

Create one public OAuth client named **THIEPN Bike Atlas** with exact redirect:

`https://thiepn.dev/bikes/auth/callback/`

Then bind that UUID to the first-party Account registry and set the Bikes repository variable `BIKES_ACCOUNT_OAUTH_CLIENT_ID`.
