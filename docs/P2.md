# P2 — Production Road R1 Asset & Semantic Component Preparation

## Goal

Turn P1's rendering engine into an asset-ready product by locking a legally usable road-bike source and defining the exact semantic model that P3 interaction will target.

## Source decision

Primary source:

- **MirageYM/3DModels — RoadBike**
- FBX source is directly available in the public repository.
- Upstream README identifies the work as reusable and CC BY 4.0.
- Repository license names Yasutoshi Mori as copyright holder.
- The RoadBike is explicitly described as modeled but without UVs.

Why this source:

1. It is a generic road-bike geometry source rather than a clone of a current branded flagship.
2. The source file is directly reproducible from GitHub.
3. CC BY 4.0 permits modification and redistribution with attribution.
4. Missing UV/material polish is acceptable because Bike Atlas should own its PBR look instead of inheriting arbitrary marketplace materials.

The source is pinned by Git blob SHA. The application repo does not vendor the 4.84 MB FBX; `npm run asset:road-r1:fetch` downloads and verifies the exact upstream blob.

## Semantic target

Road R1 now has **35 canonical selectable components**, including:

- frame and fork;
- front/rear wheel, tires, rims, hubs and thru axles;
- front/rear rotors and calipers;
- handlebar, stem and both shift/brake levers;
- saddle and seatpost;
- crankset, left/right crank, two chainrings and bottom bracket;
- chain, cassette, front/rear derailleur;
- both pedals;
- headset.

Every component has:

- stable Bike Atlas ID;
- canonical `COMP__*` node target;
- system ownership;
- material families;
- searchable tags.

P3 can therefore implement interaction against semantic IDs rather than source mesh names.

## No heuristic semantic splitting

A critical rule: **do not guess** upstream FBX object names.

Workflow:

1. Fetch source.
2. Run Blender audit.
3. Review object inventory.
4. Populate `road-r1.source-map.json` with exact mappings.
5. Run conservative preparation script.
6. Perform required manual/Blender cleanup and separation.
7. Author UVs and PBR materials.
8. Generate LODs.
9. Export GLBs.
10. Optimize with Meshopt + KTX2.
11. Validate against the P1 asset contract.

This prevents the importer from incorrectly deciding that a visually similar mesh is a derailleur, rotor, or cassette.

## Runtime budgets

| LOD | Purpose | Triangle ceiling |
|---|---|---:|
| 0 | close component inspection | 350k |
| 1 | normal desktop | 180k |
| 2 | mobile/distant | 80k |
| 3 | thumbnail/background | 20k |

These are ceilings rather than targets. Lower is preferred if silhouette and close-up quality survive.

## Texture targets

- KTX2/Basis runtime textures.
- 1K mobile/common.
- up to 2K normal desktop.
- 4K allowed only for hero close-up components where visually justified.
- Rebuild the material system around physical carbon, metal, rubber, polymer and saddle materials.

## Repository tooling added

- source attribution;
- 35-component semantic registry;
- source-object mapping file;
- Blender source audit script;
- conservative Blender preparation script;
- asset metadata validation;

- CI asset validation.

## What remains before P2 is visually complete

The source binary must be fetched in an environment with normal network access and passed through Blender. The source audit determines its real object topology; only then can semantic splitting, UV work, material authoring, retopology, and GLB export be performed accurately.

This is an asset-authoring task, not something the web renderer should fake.

## Exit gate

P2 closes completely when:

- source audit is committed;
- source map is populated;
- Road R1 working asset contains all required semantic nodes;
- materials/UVs are authored;
- LOD0–LOD3 GLBs exist;
- runtime GLBs retain attribution;
- `npm run validate:assets`, lint and build pass;
- visual inspection shows no obvious mechanical/modeling errors.
