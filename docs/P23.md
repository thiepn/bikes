# P23 — Advanced Drivetrain, Brake-System & Suspension Compatibility + Build Consequence Analysis

## Objective

Move Bike Atlas from component-by-component compatibility into system-level bicycle configuration.

P22 could answer:

```text
Does this component fit this host slot?
```

P23 adds two harder questions:

```text
If several individually compatible parts are combined,
do they work together as a bicycle system?

and

What does the resulting build change?
```

The new model therefore has three distinct layers:

```text
1. slot compatibility
2. system coherence
3. build consequence
```

A part can pass layer 1 and still fail layer 2.

That distinction is intentional.

---

## P23 build scope

P23 adds six advanced system slots:

```text

Rear derailleur
```

They join the P22 slots:

```text
Front wheel
Rear wheel
Front tire
Rear tire
Handlebar
Stem

Rear rotor
Seatpost
Saddle
Left pedal
Right pedal
```

### Slot counts

```text
Road R1       18
Gravel G1     18
MTB M1        18
Urban U1      17
```

Urban has no rear-derailleur slot because its reference drivetrain is an internal-gear system.

Bike Atlas does not create a fake derailleur merely to force every host into the same schema.

# Advanced static compatibility

## Fork

Fork compatibility checks:

```text
steerer clamp
wheel format
front axle
brake mount
axle-to-crown host envelope
```

Reference fork data also carries:

```text
suspension travel
maximum reference rotor diameter
```

Those latter properties are used by the system-consequence layer.

### Example

The Road and Gravel forks share:

```text
28.6 mm steerer
622 wheel format
12×100 thru axle
flat-mount brake interface
```

but use different authored axle-to-crown geometry.

The Gravel host accepts the shorter Road fork inside its reference envelope.

The Road host rejects the taller Gravel fork.

This deliberately demonstrates that compatibility can be asymmetric.

---

## Brake calipers

P23 caliper slot compatibility checks:

```text
brake actuation
caliper mount
```

Current reference families:

```text
Road      hydraulic / flat-mount
Gravel    hydraulic / flat-mount
Urban     hydraulic / flat-mount
MTB       hydraulic / post-mount
```

Rotor diameter is **not** evaluated as an isolated slot requirement.

It is evaluated later against the effective rotor in the complete build.

That permits Bike Atlas to model an important real-world concept:

> A caliper can mount to the frame/fork but still be wrong for the currently selected rotor setup.

---

## Cranksets

Crankset slot compatibility checks:

```text
spindle / bottom-bracket family
reference chainline envelope
chain family
```

Additional crankset system properties:

```text
ring count
small chainring teeth
large chainring teeth
```

These feed drivetrain dependency analysis.

---

## Rear transmission

P23 uses one semantic slot:

```text
rear-transmission
```

instead of pretending every bicycle has a cassette.

Current architectures:

```text
Road      external cassette
Gravel    external cassette
MTB       external cassette
Urban     internal-gear transmission
```

Slot checks include:

```text
transmission architecture
carrier / hub family
chain family
```

Additional system data includes:

```text
gear count
smallest rear sprocket
largest rear sprocket
internal gear range where applicable
```

The Urban donor uses its external hub sprocket as the visible semantic representative while preserving the internal-gear architecture in compatibility data.

---

## Rear derailleur

Road, Gravel and MTB have rear-derailleur slots.

Static checks:

```text
shift actuation family
hanger family
chain family
```

System-level properties:

```text
maximum sprocket
total capacity
```

Largest-sprocket clearance and capacity are **not** treated as isolated mounting constraints because they depend on the selected cassette and crankset.

# System consequence engine

P23 adds:

```text
domain/compatibility/analyze-build.ts
engine/compatibility/consequence-types.ts
content/compatibility/consequences.json
domain/compatibility/consequence-catalog.ts
```

The analyzer uses the effective part in every relevant slot:

```text
selected donor part
        or
installed reference part
```

and checks cross-component relationships.

## Build health

The complete draft receives one of three states:

```text
ready
attention
blocked
```

### ready

No modeled blocking or warning condition exists.

### attention

The build is mechanically coherent under current rules but has a modeled consequence requiring review.

### blocked

One or more modeled dependencies are violated.

Blocked does **not** remove the component from the draft.

That is deliberate.

The user can keep the conflicting part installed logically and make the required companion change next.

# Brake-system dependencies

## Rotor ↔ caliper

For each wheel:

```text
selected rotor diameter
        ↓
selected caliper supported range
```

A mismatch creates a blocking issue.

### Example

On Gravel G1:

```text
Road front caliper
+
Urban 180 mm front rotor
```

Both parts individually pass their Gravel mounting interfaces.

But the Road caliper's authored range is:

```text
140–160 mm
```

Therefore the complete build becomes:

```text
BLOCKED
front-caliper-rotor-range
```

This is exactly the distinction P23 was designed to introduce.

---

## Rotor ↔ fork

The selected front rotor is also checked against:

```text
selected fork maxRotorDiameter
```

A rotor can therefore pass:

```text
wheel mount
caliper range
```

and still fail the fork reference limit.

---

## Wheel ↔ rotor

P23 cross-checks:

```text
wheel disc interface
rotor disc interface
```

for both front and rear systems.

This provides a second line of defense beyond host-slot validation when multiple components are changed simultaneously.

---

# Drivetrain dependencies

## Rear wheel ↔ rear transmission

The analyzer compares:

```text
rear wheel freehub / transmission carrier
        ↔
rear transmission carrier requirement
```

This prevents a draft from becoming inconsistent after both parts are changed independently.

---

## Chain family

The analyzer cross-checks:

```text
crankset
rear transmission
rear derailleur
```

for chain-family consistency.

The actual chain is not yet a swappable P23 Build Lab slot.

That is deliberate: P23 first establishes the system dependency before adding chain-length and link-count configuration.

---

## Largest sprocket clearance

For external cassette systems:

```text
cassette largest sprocket
<=
rear derailleur maximum sprocket
```

Violation:

```text
rear-derailleur-largest-sprocket
```

---

## Total derailleur capacity

P23 calculates:

```text
required capacity =
(front large - front small)
+
(rear large - rear small)
```

and checks:

```text
required capacity
<=
selected rear derailleur capacity
```

Violation:

```text
rear-derailleur-capacity
```

---

# Companion-change example

One of the key P23 regressions is:

## Step 1 — Road R1 reference drivetrain

```text
Road crankset
Road cassette
Road derailleur

→ coherent
```

## Step 2 — install Gravel rear transmission

The Gravel cassette physically passes the Road rear-transmission slot because the modeled carrier and chain family match.

But:

```text
Gravel largest sprocket    44T
Road derailleur maximum    36T

→ BLOCKED
```

The resulting total capacity also exceeds the Road derailleur reference capacity.

This proves:

```text
slot compatible
≠
system compatible
```

## Step 3 — install Gravel rear derailleur

The Gravel derailleur reference is authored for:

```text
46T maximum sprocket
50T total capacity
```

The Road + Gravel-transmission combination is then coherent under the current P23 dependency model.

The Build Lab does not silently change the derailleur.

The user sees the conflict and chooses the companion part.

# 1× / 2× consequences

Crankset topology is also analyzed.

## Multi-ring crankset

If:

```text
ringCount > 1
```

the host must contain an authored:

```text
front derailleur
front shift control
```

Otherwise the draft is blocked.

### Gravel + Road crankset

The Road reference crankset is a 2× system.

Gravel G1 has no authored front derailleur.

Therefore:

```text
Road crankset physically fits Gravel reference mount
        ↓
but complete drivetrain lacks front shifting
        ↓
BLOCKED
```

## 1× on a 2× host

If Road R1 receives a 1× crankset:

```text
front derailleur becomes redundant
```

P23 reports this as a warning.

It does not silently remove the front derailleur from the 3D model.

A later configuration/removal phase can make that explicit.

# Fork and suspension consequences

P23 checks the selected fork against the reference fork.

Metrics:

```text
suspension travel delta
axle-to-crown delta
```

If axle-to-crown changes by at least 15 mm:

```text
warning: fork geometry change
```

If suspension travel changes by at least 20 mm:

```text
warning: material travel change
```

These are directional warnings only.

P23 does **not** yet calculate the resulting:

- head angle;
- trail;
- wheelbase;
- stack;
- reach;
- bottom-bracket height.

That belongs to the full geometry consequence solver.

# Build consequence metrics

The Build Lab now shows live:

```text
mass delta
CdA delta
front brake leverage delta
rear brake leverage delta
gear range
fork axle-to-crown delta
```

## Brake leverage metric

P23 currently uses:

```text
relative rotor leverage
=
selected rotor diameter
/
reference rotor diameter
```

This is a mechanical leverage reference only.

It is **not** a stopping-distance prediction.

It does not model:

- pad compound;
- caliper piston area;
- tire grip;
- weight transfer;
- heat;
- hydraulic leverage;
- road surface.

---

## Gear range

For external drivetrains:

```text
low ratio =
front small / rear large

high ratio =
front large / rear small

gear range =
high / low
```

For the Urban internal-gear reference, P23 uses its authored internal range together with the primary chain ratio to generate an educational low/high reference span.

# Physics Lab propagation

P23 adds:

```text
domain/compatibility/physics-effects.ts
```

The active custom build now alters Physics Lab's baseline.

## Mass

```text
custom bike mass =
reference bike mass
+
sum(selected part mass - installed part mass)
```

## Aerodynamics

Handlebar swaps contribute a reference CdA delta:

```text
custom CdA =
reference CdA
+
selected cockpit contribution
-
installed cockpit contribution
```

Example reference delta:

```text
Road → Gravel handlebar
mass   +0.06 kg
CdA    +0.03 m²
```

These are intentionally simplified educational deltas.

---

## Tires

A changed front or rear tire contributes half of the donor archetype's reference difference in:

```text
surface Crr
wheel circumference
```

Changing both tires to one donor family therefore moves the host to the donor's full reference tire-related delta.

This remains an archetype-level reference approximation.

---

## Rear transmission

A changed rear transmission can propagate the donor drivetrain family's reference efficiency into Physics Lab.

This is not a component bench-test efficiency measurement.

---

## Blocked builds in Physics

Bike Atlas does **not** disable Physics when a custom build is blocked.

Instead it displays:

```text
Simulation is provisional
```

with the Build Lab system-health state.

This allows experimentation while preventing a mechanically incoherent draft from being presented as a valid bicycle configuration.

Manual Physics overrides still work on top of the build-adjusted baseline.

---

# Persistent custom bike state

P22 tied visible donor geometry closely to the open Build panel.

P23 separates:

```text
build=1
```

from:

```text
buildParts=...
```

Meaning:

```text
build=1
→ Build Lab panel is open

buildParts
→ custom bicycle draft exists
```

Closing the Build panel no longer destroys the custom bicycle.

The draft persists across compatible Explore tools such as Physics.

The 3D scene continues rendering it.

Host-changing workflows still clear the draft.

# Model boundary

P23 is still an educational reference system.

It does not yet certify:

- real manufacturer cross-compatibility;
- chain length;
- actual chainline under load;
- front derailleur cage geometry;
- exact shifter cable pull;
- hydraulic hose/fitting standards;
- brake adapter stack;
- thermal brake performance;
- structural load limits;
- fork/frame warranty limits;
- tire/frame collision;
- dynamic suspension kinematics;
- exact geometry after fork changes.

Those are intentionally not inferred from missing data.
