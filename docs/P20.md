# P20 — Bicycle Physics Lab & Performance Simulation

## Objective

Add an inspectable physics model to Bike Atlas that estimates bicycle performance from explicit assumptions instead of attaching fake fixed values such as “maximum speed” to a bicycle type.

P20 answers questions such as:

- What steady speed does a reference bike reach at a given rider power?
- How much does a climb change the result?
- What does a headwind cost?
- How much does cargo matter uphill?
- How do the four Bike Atlas archetypes compare under the same rider and environment?
- What cadence corresponds to a speed in an explicitly selected drive ratio?
- How much power would that cadence-selected speed require?

## Core rule

Bike Atlas keeps two different relationships separate:

```text
physics:
rider power + forces → sustainable steady speed

kinematics:
cadence + drive ratio + wheel circumference → wheel speed
```

A gear ratio does **not** create sustainable speed by itself.

A rider can select a ratio that implies 45 km/h at 90 rpm, but if the current aerodynamic, rolling and climbing demand requires 500 W while the rider provides 250 W, 45 km/h is not a steady-state result.

## Physics model

P20 uses a transparent longitudinal steady-state model.

### Grade angle

```text
θ = atan(grade / 100)
```

### Total system mass

```text
m =
  rider mass
+ cargo mass
+ bicycle mass
```

### Rolling resistance

```text
F_roll = Crr · m · g · cos(θ)
```

### Gravity

```text
F_gravity = m · g · sin(θ)
```

Positive grade creates positive climbing resistance.

Negative grade creates a negative gravity term and therefore assists motion.

### Relative air speed

Bike Atlas defines:

```text
positive wind = headwind
negative wind = tailwind
```

Then:

```text
v_air = v_ground + v_wind
```

### Aerodynamic force

```text
F_aero =
  0.5 · ρ · CdA · v_air · |v_air|
```

The signed air-speed term means a tailwind faster than the bicycle can produce a forward aerodynamic force rather than impossible positive drag.

### Required wheel power

```text
P_required =
  (F_roll + F_gravity + F_aero)
  · v_ground
```

### Available wheel power

For positive pedaling power:

```text
P_wheel =
  P_rider · drivetrain efficiency
```

P20 numerically solves:

```text
P_wheel = P_required
```

for steady ground speed.

### Zero-power descending case

At zero rider power, simply solving power equality would always include the trivial solution:

```text
v = 0
```

even on a downhill.

P20 therefore handles zero-power descending separately and solves the **force equilibrium**:

```text
F_roll + F_gravity + F_aero = 0
```

when gravity or wind can accelerate the bicycle.

## Cadence model

Cadence is calculated separately.

For an explicitly selected overall drive ratio:

```text
wheel rpm =
  cadence rpm · drive ratio
```

and:

```text
speed =
  wheel rpm
  · wheel circumference
```

P20 intentionally uses an editable **overall drive ratio** instead of inventing cassette tooth counts or internal-hub ratios not defined in the current archetype data.

## Reference bicycle assumptions

All values below are tagged:

```text
source = bike-atlas-reference
```

They are simulation defaults, not manufacturer measurements.

| Bike | Bike mass | CdA | Drivetrain efficiency | Wheel circumference | Default drive ratio |
| --- | ---: | ---: | ---: | ---: | ---: |
| Road R1 | 8.5 kg | 0.32 m² | 0.975 | 2.11 m | 2.80× |
| MTB M1 | 14.5 kg | 0.50 m² | 0.965 | 2.31 m | 1.35× |
| Urban U1 | 18.0 kg | 0.66 m² | 0.950 | 2.16 m | 2.00× |
| Gravel G1 | 10.0 kg | 0.38 m² | 0.970 | 2.18 m | 2.20× |

### Why CdA is not a bike-only property

The reference CdA includes a representative rider posture.

It therefore represents:

```text
rider + bicycle frontal/aerodynamic system
```

and must not be interpreted as frame drag alone.

## Surface model

P20 starts with five surface presets:

```text
Smooth asphalt
Rough asphalt
Hardpack gravel
Loose gravel
Trail
```

Each bicycle archetype has an effective reference Crr for each surface.

These values are **educational effective coefficients**, not laboratory measurements of a specific tire.

They also compress effects that a simple longitudinal Crr model cannot separately represent, especially on rough terrain.

## Editable assumptions

The active bicycle exposes editable assumptions for:

```text
bike mass
CdA
drivetrain efficiency
Crr
air density
drive ratio
```

Every edited value can be reset to the Bike Atlas reference value.

This is important because rider posture, tire choice, pressure, road condition, luggage and drivetrain state can move real-world values substantially.

## Rider / environment controls

Current ranges:

```text
rider power       0–600 W
rider mass       40–140 kg
cargo             0–40 kg
grade            -15–20%
wind             -40–60 km/h
cadence           40–140 rpm
drive ratio        0.5–5.0×
air density        0.8–1.4 kg/m³
```

Positive wind means headwind.

Negative wind means tailwind.

## Quick scenarios

P20 includes one-click starting points:

```text
Flat road
7% climb
Gravel
Headwind
```

These are convenience presets only. All inputs remain editable.

## Live result

The active bike result displays:

- estimated steady speed;
- rider power;
- wheel-side power after drivetrain loss;
- total system mass;
- largest positive power demand.

P20 also decomposes wheel-side demand into:

```text
Aerodynamic power
Gravity power
Rolling-resistance power
--------------------------------
Required wheel power
```

Negative gravity power on a descent is displayed as a negative contribution rather than hidden.

## Four-bike comparison

The same rider/environment scenario is run across:

```text
Road R1
MTB M1
Urban U1
Gravel G1
```

so the user can see how the reference assumptions change the equilibrium result.

The active bike uses any current manual assumption edits.

The other three retain their Bike Atlas reference profiles.

## Reference sanity scenario

The validation suite uses the following scenario:

```text
250 W rider power
75 kg rider
0 kg cargo
0% grade
0 km/h wind
1.225 kg/m³ air density
smooth asphalt
```

Current reference outputs are approximately:

```text
Road R1    36.9 km/h
Gravel G1  34.4 km/h
MTB M1     29.5 km/h
Urban U1   28.2 km/h
```

These are **model sanity outputs**, not promises about real bicycles.

At the same 250 W on a 7% grade:

```text
Road R1    13.9 km/h
Gravel G1  13.3 km/h
MTB M1     11.8 km/h
Urban U1   11.7 km/h
```

The validation checks relationships rather than freezing every displayed decimal.

## Cadence / gearing panel

P20 reports:

### Speed implied by cadence

Example conceptually:

```text
90 rpm
× 2.80 overall drive ratio
× wheel circumference
→ kinematic speed
```

### Power required at that speed

The same kinematic speed is fed back into the physical resistance model.

The UI then shows whether the entered rider power is:

```text
above required power → positive margin
below required power → shortfall
```

### Cadence at physics equilibrium

The lab also reports what cadence the selected drive ratio would require at the calculated steady-state speed.

## Shareable scenarios

Opening Physics adds:

```text
physics=1
```

Non-default scenario values are serialized into query parameters.

Supported parameters:

```text
pwr      rider power
rider    rider mass
cargo    cargo mass
grade    grade %
wind     wind km/h
rho      air density
surface  surface preset
cad      cadence
ratio    drive ratio

bm       custom bike mass
cda      custom CdA
eta      custom drivetrain efficiency
crr      custom rolling resistance
```

Example:

```text
/?bike=gravel-g1&physics=1&pwr=250&grade=7&wind=10&surface=hardpack-gravel&cargo=5
```

Closing Physics removes all Physics-specific query state.

Entering Story, Learn or Workshop also clears it.

## Model boundary

P20 deliberately does **not** model:

- acceleration;
- sprint dynamics;
- cornering;
- braking;
- traction limits;
- rider fatigue;
- changing body position;
- gusting/crosswind dynamics;
- tire deformation beyond effective Crr;
- detailed suspension dynamics;
- terrain impacts;
- drivetrain losses by individual gear;
- wheel rotational inertia;
- manufacturer-specific component data.

The result is therefore:

```text
educational steady-state estimate
≠ race prediction
≠ manufacturer test
≠ guaranteed real-world speed
```

## Validation

P20 adds:

```text
scripts/validate-physics.mjs
```

It validates:

- one physics profile per current archetype;
- reference-data labeling;
- surface coverage;
- sensible bounds for mass / CdA / efficiency / wheel circumference;
- Crr presence for every surface;
- force-model terms;
- cadence/physics separation;
- flat-reference ordering;
- 7% climb reducing speed;
- headwind reducing speed;
- cargo reducing uphill speed;
- editable assumption UI;
- four-bike comparison;
- shareable Physics URL state;
- Physics viewer routing;
- Escape behavior.

It is included in:

```bash
npm run validate:domain
```
