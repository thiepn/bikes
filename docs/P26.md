# P26 — Interactive Optimization Frontier, Pareto Trade-Offs & Build Comparison

## Objective

P26 extends P25 from one weighted ranking into a two-objective trade-off explorer.

Instead of asking only:

- What is the highest-scoring build for Speed?
- What is the highest-scoring build for Comfort?

the user can now ask:

- Which builds are non-dominated when Speed and Comfort are considered together?
- How much of one objective is traded for another?
- Which frontier point should become the active custom bicycle?

P26 uses the same compatibility, system-health, geometry, gearing and Physics models as P25.

## Product structure

Optimize now has two views:

- Ranked — P25 single-goal optimization
- Frontier — P26 explored Pareto trade-offs

The same hard constraints are shared by both views:

- maximum component changes
- Strict / Balanced / Open geometry guard
- preserve-current-modified-slots

Switching views does not create a second custom-bike state.

## Explored Pareto frontier

P26 deliberately uses the term explored Pareto frontier.

It does not claim an exhaustive global optimum over every possible bicycle.

The frontier is calculated from the bounded fictional Bike Atlas donor graph and the active P25 search constraints.

A point is non-dominated when no other explored coherent candidate is at least as good on both chosen objective scores and meaningfully better on at least one.

Near-identical score pairs use fewer changed components as the tie-break.

## Multi-objective search

P26 samples five weighted P25 searches between the chosen X and Y goals:

- 0 / 100
- 25 / 75
- 50 / 50
- 75 / 25
- 100 / 0

The candidate unions are deduplicated by canonical build selection encoding.

Each unique build is then rescored independently on the actual X and Y goal models.

The five search sweeps are a deliberate bounded approximation that preserves P25 companion-aware mechanics rather than introducing a second unrelated optimizer.

## Current build reference

The active custom bicycle is plotted as the current reference point.

If the current build is mechanically coherent, it participates in dominance filtering.

Therefore any candidate that is worse than the current build on both chosen objectives is removed.

If the current build is blocked, it is still shown as a visual reference but does not dominate coherent alternatives.

## Objective axes

Any two distinct P25 goals can be selected:

- Speed
- Climbing
- Mixed Surface
- Comfort
- Utility

The axis selector prevents identical X and Y goals during normal interaction.

Malformed deep links that specify the same axis twice are automatically repaired to a distinct second goal.

The axes are goal scores from 0–100 using the same transparent P25 feature model.

## Frontier chart

The P26 chart uses a fixed 0–100 coordinate system.

It renders:

- X-goal score
- Y-goal score
- explored non-dominated build points
- connecting frontier line
- current-build diamond
- selected point
- comparison-pinned point

Frontier points are keyboard focusable.

Enter or Space selects the focused point.

## Frontier navigation

The user can:

- click a point
- focus and activate a point by keyboard
- move through points with previous/next buttons
- move along the ordered frontier with a range slider
- swap X and Y axes

Frontier points are ordered primarily by increasing X score and then decreasing Y score.

## Comparison pin

Any selected frontier build can be pinned for comparison.

The user can then move to another frontier point and compare:

- X objective score
- Y objective score
- flat speed
- climbing speed
- hardpack speed
- mass
- lowest gear
- tire width

The comparison section reports selected-minus-pinned numeric deltas.

This lets users inspect the cost of moving along the trade-off curve rather than relying on one aggregate score.

## Configuration inspection

Each selected frontier point exposes the exact changed component slots and selected donor parts.

The active P25/P23 mechanical-health constraints have already been applied before the point can appear on the final frontier.

## Apply flow

P26 uses the same canonical build application path as P25.

Apply frontier build:

- writes the selected frontier configuration into buildSelections
- updates buildParts URL state
- updates the 3D scene
- updates Geometry
- updates Physics

Apply + inspect in Build Lab:

- applies the same configuration
- closes Optimize
- opens Build Lab
- allows direct inspection of component and system consequences

There is no frontier-owned bicycle copy.

## URL state

P26 extends Optimize URL state with:

- optView=frontier
- optX=<goal>
- optY=<goal>
- optPoint=<frontier index>

Existing P25 hard-constraint state remains:

- optChanges
- optGuard
- optPreserve

The actual bicycle remains encoded in buildParts.

When returning to Ranked view, Frontier-specific query state is removed.

## Performance behavior

The ranked P25 search is not also computed when Frontier view is open.

P26 performs its own five bounded P25 sweeps only while Frontier is active.

This prevents the app from needlessly running both optimization workspaces simultaneously.

## Dominance details

P26 uses a score epsilon of 0.05.

Candidate A dominates B when:

1. A is no worse than B on both objective scores within epsilon, and
2. A is meaningfully better on at least one objective,

or when both scores are effectively equal and A requires fewer component changes.

This avoids duplicate near-identical frontier points that only add unnecessary changes.

## Model boundary

P26 remains an educational configuration explorer.

The frontier is not:

- an exhaustive mathematical proof over all real bicycle parts
- purchasing advice
- manufacturer certification
- structural engineering
- personal bike fitting
- a price/value optimizer
- real inventory optimization
- measured race-performance prediction

It is a transparent non-dominated set within the explored Bike Atlas reference space.

## Validation

P26 adds scripts/validate-pareto.mjs to npm run validate:domain.

The validator protects:

- five-sweep frontier definition
- shared P25 scoring
- distinct-axis requirement
- current-build dominance semantics
- blocked-current exception
- fewer-changes tie-break
- coherent-only frontier points
- Pareto point/result types
- Ranked / Frontier view separation
- conditional ranked compute
- X/Y controls
- axis swap
- SVG frontier visualization
- keyboard-accessible points
- slider navigation
- comparison pin
- selected-vs-pinned metrics
- apply flow
- P26 query keys
- malformed duplicate-axis repair
- P26 visual selectors
